    Storage Benchmark Runbook¶

    Compare the I/O performance of two storage classes on the same node with kbench (a fio wrapper from the Longhorn authors). Use it to answer questions like "how much slower is Longhorn than local disk on this worker?" or "did the new disk / network / StorageClass setting actually help?".

    When to Use¶

    • Before and after changing Longhorn settings (replica count, data locality, disk selector)
    • After hardware changes (new NVMe, 10GbE storage network, see Storage Network Runbook)
    • When slow I/O is suspected and you need numbers

    Manifests¶

    Both manifests create two 31Gi PVCs and a one-shot Job that runs cmp_run.sh, which benchmarks the first volume against the second.

    File Volume 1 Volume 2 Node
    kbench-localpath-vs-longhorn.yaml local-path longhorn k3sworker06
    kbench-localpath-vs-longhorn-test.yaml local-path longhorn-test k3sworker05

    longhorn-test is defined in cluster-critical-apps/longhorn-system/templates/storageclass-test.yaml (3 replicas, diskSelector: ssd, pinned to k3sworker05, dataLocality: best-effort). Edit it to try different Longhorn parameters without touching the production longhorn class.

    kbench-localpath-vs-longhorn.yaml 
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: kbench-pvc-1
spec:
  volumeMode: Filesystem
  #volumeMode: Block
  #storageClassName: longhorn  # replace with your storage class
  storageClassName: local-path
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 31Gi
---
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: kbench-pvc-2
spec:
  volumeMode: Filesystem
  #volumeMode: Block
  storageClassName: longhorn  # replace with your storage class
  #storageClassName: local-path
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 31Gi
---
apiVersion: batch/v1
kind: Job
metadata:
  name: kbench
spec:
  template:
    metadata:
      labels:
        kbench: fio
    spec:
      nodeSelector:
        kubernetes.io/hostname: k3sworker06
      containers:
      - name: kbench
        image: yasker/kbench:latest
        imagePullPolicy: Always
        env:
        #- name: QUICK_MODE  # for debugging
        #  value: "1"
        - name: FIRST_VOL_NAME
          value: Local-Path
        - name: FIRST_VOL_FILE
          value: "/volume1/test"
        - name: SECOND_VOL_NAME
          value: Longhorn
        - name: SECOND_VOL_FILE
          value: "/volume2/test"
        - name: SIZE
          value: "30G" # must be smaller or match the PVC size
        - name: CPU_IDLE_PROF
          value: "disabled" # must be "enabled" or "disabled"
        volumeMounts:
        - name: vol1
          mountPath: /volume1/
        - name: vol2
          mountPath: /volume2/
        command: ["bash", "/fio/cmp_run.sh"]
        #volumeDevices:
        #- name: vol1
        #  devicePath: /volume1/test
        #- name: vol2
        #  devicePath: /volume2/test
      restartPolicy: Never
      volumes:
      - name: vol1
        persistentVolumeClaim:
          claimName: kbench-pvc-1
      - name: vol2
        persistentVolumeClaim:
          claimName: kbench-pvc-2
  backoffLimit: 0

    Procedure¶

    1. Pick the node and storage classes. Adjust nodeSelector, the PVC storageClassNames and the FIRST_VOL_NAME / SECOND_VOL_NAME labels. The node needs at least ~31Gi free for each volume. SIZE must be at or below the PVC size.

    2. Run it in a scratch namespace:

      kubectl create namespace kbench
kubectl -n kbench apply -f docs/runbooks/storage-benchmark/kbench-localpath-vs-longhorn.yaml

    3. Wait and read the results. A full run takes a while (tens of minutes with 30G). Set QUICK_MODE=1 in the Job env to check the setup first.

      kubectl -n kbench get pods -l kbench=fio -w
kubectl -n kbench logs -l kbench=fio -f

      The final summary compares IOPS, bandwidth and latency (random/sequential, read/write) for both volumes.

    4. Record the results next to earlier runs (see docs/Performance.numbers).

    5. Clean up. The PVCs hold 2×31Gi, so delete them:

      kubectl delete namespace kbench

    Variations¶

    • Block mode: switch both PVCs to volumeMode: Block and replace volumeMounts with the commented-out volumeDevices block. This removes filesystem overhead from the measurement.
    • CPU idle profiling: set CPU_IDLE_PROF=enabled to also report CPU usage during the test.

    • Single volume: kbench also supports run.sh with only FILE_NAME set. See the kbench README.

    • [CSI]: Container Storage Interface

    • [IOMMU]: Input-Output Memory Management Unit. Used to virualize memory access for devices. See Wikipedia
